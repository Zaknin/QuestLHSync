## Scope and evidence boundary

It did not invoke ADB, inspect a live process, open a camera, create an approval, access root, read process memory, change logging, use tracing, start SteamVR, or enable Lighthouse correction. The private provider ELF was read from its existing canonical ZIP into a temporary host directory for metadata inspection and was not added to Git. No full disassembly is reproduced here.

The owner-confirmed target remains a Pico 4 Pro on international Pico OS. The Android property tuple and fingerprint identify the observed software build; they are not cryptographic hardware attestation.

Both libraries have version-need metadata for platform symbols, but the CSL registration import/export itself is not symbol-versioned. Android's dynamic linker still has to resolve every dependency in the namespace selected for the process. Android 10 AOSP uses linker configuration to assign executable paths to namespaces and control namespace search/permitted paths and links; see the [Android 10 Bionic linker implementation](https://android.googlesource.com/platform/bionic/+/refs/heads/android10-c2f2-s2-release/linker/linker.cpp), the [AOSP linker configuration format](https://android.googlesource.com/platform/bionic/+/master/linker/ld.config.format.md), and the [VNDK namespace overview](https://source.android.com/static/docs/core/architecture/images/VNDK.pdf). These are platform references, not PICO files. The exact PICO linker config, QuickCamera process executable path, namespace assignment, and resolved dependency list are absent from the existing evidence. Therefore the /vendor/lib64 placement and DT_NEEDED relationship are compatible with a vendor-library resolution, but do not prove which file the device linker loaded.

## Static CRM → CSL → QuickCamera facts

The acquired provider has a direct V4L2 subscribe/dequeue implementation and a callback-registration/dispatch path. Its inspected event parser reads CRM request ID, frame ID, timestamp, link handle, and event ID fields; the dispatch path copies request ID into CSLMessage +0x08, frame ID into +0x10, timestamp into +0x18, and then invokes the stored callback indirectly. QuickCamera's pinned CSLMessageHandler reads the request ID at +0x08 and a 64-bit timestamp-sized field at +0x18; its registration call imports the matching unversioned symbol and declares the provider as a dependency.

The static bridge is now verified for the installed provider binary and the pinned QuickCamera binary. It is still not runtime evidence. In particular:

- Installed provider identity is verified by the bounded M2.7B acquisition and archive read-back. Runtime-loaded provider identity is not observed.
- The provider has a callback dispatch implementation and QuickCamera registers a callback. No evidence says that this callback ran in a live process.
- The provider has event-ID branches for 0 and 2. Event 0 writes marker words 0/0; event 2 writes 1/1. These values structurally match public CamX's mapping of SOF ID 0 to Qtimer/bNotify=false and SOF_BOOT_TS ID 2 to Mono/bNotify=true. The timestampType/bNotify meanings remain a cross-source interpretation until the exact running kernel contract is tied to this firmware.
- In the inspected provider dispatch path, zero request ID passes for event IDs 0 and 1, while IDs greater than 1 are skipped. Thus a zero-request-ID event 2 is not dispatched along that path. This is a static branch observation, not a kernel guarantee, and no runtime count is known.
- The provider copies its 64-bit timestamp field into the CSL message without an observed conversion in that bridge. Its bits could be raw QTIMER ticks, QTIMER-derived nanoseconds, BOOTTIME/monotonic nanoseconds, or another kernel-selected value. Marker values alone do not identify units, epoch, or clock domain.
- The QuickCamera handler stores timestamp data in a 38-slot request-indexed ring. Static code includes a timeout fallback that selects the previous ring slot. Neither fallback selection nor its frequency has been observed at runtime.
- CRM request ID, CSL sync request ID, pipeline request ID, and PVR frame ID are distinct namespaces unless an explicit mapping is observed. Public CamX source contains a CSL-to-pipeline request remap. The provider's CRM-to-CSL field copy does not prove equality with a pipeline ID or PVR FrameMetaDate identifier.
- Static PVR code copies metadata fields into FrameMetaDate; no live metadata record has been observed. The QuickCamera handler's field reads do not by themselves establish PVR frame identity.

## What can be learned without a camera

A read-only maps snapshot can establish whether an already-running process currently maps the provider, provided the process and mapping are readable. It does not make CRM SOF callbacks occur. Event IDs 0 and 2 are frame/request events; without an already-active normal camera stream there may be no new such event to observe. Reading an existing default log buffer can only find records that were naturally emitted before the query. No safe static query can prove a callback occurred.

Therefore no proposed no-camera method can guarantee observation of separate SOF and BOOT_TS callbacks, request/frame correlation, fallback occurrence, or FrameMetaDate values. Starting a camera, changing logging, or adding an agent is not part of this proposal. If later event evidence remains necessary, it requires a separate scope decision for passive capture during an independently occurring normal camera session; logs must already be enabled at default level and must expose the necessary identifiers without instrumentation. If those conditions are not met, callback and frame metadata claims remain blocked without invasive instrumentation.

## Minimum next runtime experiment recommendation

The highest-value, lowest-impact next step is a new, separately authorized read-only-runtime-provider-map-snapshot action. It should:

1. Recheck the exact software fingerprint and ABI, then enumerate only the existing bounded QuickCamera/PVR process-name allowlist.
2. For each validated numeric PID, read only /proc/<pid>/maps through one fixed probe and emit only rows whose paths exactly match the two allowlisted library basenames; never return raw maps.
3. Record the PID/name, map range, file offset, device major/minor, inode, permissions, and exact allowed path. At the same time, read only device/inode/size for /vendor/lib64/camx_core.so; hash that exact installed file only if the future action's explicit allowlist and cost limit permit it.
4. Stop on permission denial, PID exit, malformed output, unexpected path, timeout, or record cap. Do not try alternate privilege levels.
5. Use a new action-specific authorization, a short 15-second ceiling, and no more than 40 returned observations. This does not reuse M2.7B authorization.

**Experiment PASS:** one positively identified QuickCamera process has both the pinned QuickCamera mapping and /vendor/lib64/camx_core.so mapping; provider path, device/inode, size, and (if collected) SHA-256 correspond to the installed provider artifact in the same sampling window. This passes only the claim that the expected provider file was mapped in that process at that time.

**Experiment PARTIAL:** provider mapping is visible but the process, inode/device identity, current file hash, or companion QuickCamera mapping is incomplete.
**Experiment BLOCKED:** maps are denied, the process exits, no relevant PID is available, the mapping is absent, or an output/limit error prevents a trustworthy observation. Do not turn a blocked snapshot into an absence claim.

This experiment would not establish callback execution, event ID 0/2 occurrence, timestampType/bNotify runtime values, CRM/CSL/pipeline/PVR identifier equality, 38-slot fallback occurrence, FrameMetaDate runtime contents, QTIMER/BOOTTIME/Android clock equivalence, physical SOF/exposure start, Lighthouse suitability, pose or shared-buffer identity. An optional later read of existing logs could only advance the particular fields explicitly present in those logs; it would not satisfy missing kernel build mapping or physical-event proof.
