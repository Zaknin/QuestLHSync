# P3-A6-M2.9 — Exact Kernel Timestamp Provenance

Date: 2026-10-20
Repository baseline: `ea58e93e28c52496b7e6ee847c0844250ff9276d`
Branch: `feature/pico-support`
Scope: offline source and existing binary/evidence audit only. No ADB, logcat, camera, root, process inspection, or Lighthouse action was performed.

## Executive result

**`EXACT_KERNEL_MAPPING_UNAVAILABLE`. NO-GO for using the present QuickCamera/PVR timestamp as an exact Lighthouse synchronization time.**

The pinned ByteDance Phoenix kernel source establishes a detailed SOF timestamp path for its own revision. The acquired Pico `camx_core.so` statically dequeues CRM events and copies their timestamp field into `CSLMessage+0x18`; QuickCamera statically reads that field and can place it in its 38-slot ring. These are independently verified source and binary facts, but there is no evidence that the running kernel on the target firmware is the pinned source build, no runtime observation of the selected event or timestamp branch, and no physical sensor/exposure contract.

The closest defensible description is conditional: **in the pinned Phoenix online-CSID path, the value begins as a counter read from CSID registers named for the current SOF timestamp, is converted from 19.2 MHz QTIMER ticks to integer nanoseconds, and a companion BOOTTIME value is derived using a sampled offset.** The same source has offline BOOTTIME and frame-header alternatives. The installed provider copies the event timestamp bits unchanged, but the runtime event ID/source is unknown. Therefore the payload cannot currently be labeled globally as raw QTIMER ticks, converted nanoseconds, BOOTTIME, Android monotonic time, sensor exposure start, or callback delivery time.

### Identifier interpretation

The provider statically copies the CRM request field into `CSLMessage+0x08` and CRM `frame_id` into `CSLMessage+0x10`. QuickCamera uses `+0x08` to index the 38-slot ring and passes `+0x10` as the log's `frameCount`. This proves static field flow at those boundaries, not equality with pipeline request IDs, buffer IDs, PVR queue IDs, frame delivery order, or `FrameMetaDate` IDs. The public CamX source demonstrates a CSL-sync-ID to pipeline-request-ID remapping table; it is a source-family example, not proof of the Pico provider's runtime ID namespace. Under fallback, the selected timestamp can originate from the previous ring slot while metadata records the current request ID.

## Existing PVR timing evidence: separate boundary

The project has a private 1,204-frame PVR/K0 capture and static PVR service/camera ELF analysis ([K0 source/slot audit](P2-K0-SourceAndSlot130-20261016.md), [P2 clock-provenance closeout](P2-Closeout-P3-Clock-Provenance-20261017.md)). Those records show that PVR `FrameMetaDate` values flow into K0 slots and that a separate PVR QTIMER-like counter was compared with CNTVCT/BOOTTIME. The observed K0 slot+130 value was computed from slot+122 with a constant 225,997 ns difference in that capture. This does **not** identify the source of the CRM/CSL `+0x18` field, prove the active QuickCamera listener instance for every K0 stream, or label slot+130 as exposure time. In particular, the separately measured PVR QTIMER implementation is not proof that the camera CRM timestamp is the same counter or event.

No private capture values, serials, ELF bytes, or raw disassembly are copied into this report.

### Recommendation

**NO-GO for Lighthouse synchronization or timestamp correction now.** Do not enable any correction gate. End the exact-source search at `EXACT_KERNEL_MAPPING_UNAVAILABLE`; further searches for similar Qualcomm revisions have low expected value. The next technically useful path is a focused B+C experiment design: first confirm that an ordinary PVR metadata surface can provide timestamp plus request/frame correlation without protected memory access, then pair that same output with a hardware-timed optical event and Android/host monotonic brackets. If no safe metadata surface can provide a frame join, do not run a free-standing optical test and claim it validates the CSL timestamp.

An optical success could support a calibrated relation between the observed software timestamp and the tested optical transition for that build and configuration. It would still require separate evidence for camera identity/orientation, Lighthouse geometry, pose clock mapping, drift and uncertainty before any synchronization use. A callback log or version match alone cannot substitute for this calibration.

## Minimum missing evidence

1. **Kernel mapping:** a hash-identified kernel/boot artifact from the exact target fingerprint plus matching device-tree/config/build metadata or vendor source manifest that resolves it to a source revision. The provider ELF Build ID is not a kernel Build ID.
2. **Runtime timestamp branch:** evidence of CRM event ID, provider marker pair (`timestampType`/`bNotify`), and whether online CSID, offline BOOTTIME, or frame-header path was selected for the stream.
3. **Runtime event and ID join:** a record of the same event's CRM request/frame values, CSL request/frame values, PVR queue/frame identity and `FrameMetaDate`; explicitly record the timestamp-source request ID when fallback selects a prior ring slot.
4. **Clock contract:** exact producer source, counter scale, conversion/truncation, epoch/offset, reset/sleep behavior, and paired Android monotonic plus delivery-clock brackets with uncertainty.
5. **Physical semantics:** sensor/CSID timing contract or an independently time-referenced optical experiment on the same stream that resolves exposure start/readout/rolling-shutter phase. CSI receive, CSID SOF, kernel notification, userspace callback and exposure start must remain separate candidate events.
6. **Lighthouse suitability:** validated camera-to-headset geometry, pose timestamp domain, host clock relation/drift and held-out validation. Timestamp provenance alone does not verify pose or mapping.
