## Итоговый статус

Phoenix source pin now defines a concrete CSID→IFE→ISP→CRM SOF path, an AArch64-compatible CRM frame-message layout, and the generic V4L2 kernel subscription/dequeue dispatch. Its source is compatible with the reported Android 10 / Linux 4.19.81 family, but no build mapping proves it is the exact running kernel. The CRM fields at offsets **+0x08** (request ID) and **+0x18** (timestamp) match the two offsets read by SHA-pinned quickcamera.core.so; this is ABI compatibility evidence only. The outer envelopes differ, and no userspace subscription/dequeue path connecting the CRM V4L2 event to CSLMessageHandler was found.

## 2. SOF source-to-sink trace

### 2.1 CSID registers and timestamp conversion

The CSID driver reads csid_*_timestamp_curr1_sof_addr first as the high 32 bits and curr0 as the low 32 bits, then forms a 64-bit counter for pixel paths IPP/PPP and RDI/UDI paths. It does not read the prev* registers in this function. Reads use cam_io_r_mb. The constants are CAM_IFE_CSID_QTIMER_MUL_FACTOR=10000 and DIV_FACTOR=192; the counter is converted to integer nanoseconds as ticks * 10000 / 192 (about 52.0833 ns/tick, corresponding to 19.2 MHz). This is converted QTIMER-based nanoseconds, not raw ticks.

The CSID code then lazily calculates one static qtime_to_boottime offset from get_monotonic_boottime64() minus the converted QTIMER value. It adds that offset to form boot_timestamp; the source comment describes a “universal” camera offset. This code does not continuously recalibrate that offset. Thus the returned pair is (converted QTIMER-origin nanoseconds, derived BOOTTIME nanoseconds), subject to the chosen runtime register path and source applicability. It does not produce wall-clock UTC.

The exact register table depends on CSID variant. The pinned dispatcher cam_ife_csid17x.c maps device-tree compatibles for qcom,csid170, csid170_200, csid175, csid175_200, and csid480 to separate data tables. Examples from the tables: CSID170 pixel current SOF offsets 0x290/0x294, RDI0 0x390/0x394; CSID175 and CSID480 also include pixel mappings at 0x790/0x794 for a separate resource table. The actual device-tree compatible and selected table for this runtime are not present in the supplied evidence.

### 2.2 IFE hardware manager and ISP context

For an online SOF path, cam_ife_hw_mgr_handle_hw_sof handles VFE CAMIF/RD inputs (and RDI-only contexts), checks dual-IFE IRQ alignment, then calls cam_ife_mgr_cmd_get_sof_timestamp. The latter asks the CSID resource through CAM_IFE_CSID_CMD_GET_TIME_STAMP; in a split/dual configuration it takes the left/master result. The CSID function above provides the QTIMER-ns/BOOTTIME pair.

Offline contexts use another path: cam_ife_hw_mgr_get_offline_sof_timestamp calls get_monotonic_boottime64 and writes that same BOOTTIME value to both timestamp and boot_time. An event’s timestamp field therefore is not guaranteed to be QTIMER-derived across online and offline context types.

use_frame_header_ts is an alternate path. It defaults false on context reset and can be enabled when a custom input node is acquired. IFE inserts a frame header in this mode. The buffer-done handling path decodes a 56-bit value from two header words, scales it by the same 10000/192 factor, and sends a SOF event with the request ID whose frame-header output buffer completed. At the hardware SOF callback, the IFE manager zeros the regular timestamp when this flag is set. The normal ISP SOF notifier suppresses its SOF message only when the flag is set, request ID is nonzero, and status is success; it still sends SOF_BOOT_TS. Consequently SOF and SOF_BOOT_TS can arise from different timestamp paths and be queued at different processing points. The source does not prove that this feature is enabled for the owner’s QuickCamera/PVR stream.

The frame-header SOF event takes request_id from the completed request but frame_id from the context’s current counter at buffer-done handling. No independent frame-header frame counter is copied into that CRM field, so the source alone does not prove these represent the same physical frame in every scheduling case.

The ISP context increments its own frame_id on SOF; that context counter is distinct from the 64-bit CRM request_id. Request IDs are selected from request structures in the active/wait state-machine queues, or zero is used for idle/empty-frame notifications. They are not read from the CSID timestamp registers. The source has explicit catch-up/skip paths when SOF notification is delayed (including active-request-count and bubble handling); observed gaps or zero IDs cannot be attributed to a ring fallback without further evidence.

### 2.3 CRM event envelope, subscription, and queue

The header defines outer V4L_EVENT_CAM_REQ_MGR_EVENT = V4L2_EVENT_PRIVATE_START + 0; event IDs are SOF=0, ERROR=1, SOF_BOOT_TS=2, and CUSTOM_EVT=3. The ISP builds a cam_req_mgr_message, fills u.frame_msg, and calls cam_req_mgr_notify_message with event ID and type. The device layer sets event.id and event.type, points at event.u.data, copies sizeof(struct cam_req_mgr_message) bytes, and calls v4l2_event_queue.

The CRM video device is dynamically registered as a V4L grabber with name cam-req-mgr and minor -1; its file operations route ioctl calls through video_ioctl2. The exact same-commit `v4l2-ioctl.c` maps `VIDIOC_SUBSCRIBE_EVENT` through `v4l_subscribe_event` to `ops->vidioc_subscribe_event`, and maps `VIDIOC_DQEVENT` through `v4l_dqevent` to `v4l2_event_dequeue`. The CRM callback calls `v4l2_event_subscribe`; V4L2 core stores subscription state and queues only events matching the subscribed type/id. On dequeue, the core removes the oldest queued event and copies the `struct v4l2_event` into its kernel ioctl buffer; `video_ioctl2` uses `video_usercopy` around `__video_do_ioctl`, which returns the result through the ioctl copy-out path. Thus the kernel contract preserves the queued event's `type`, `id` and 64-byte `u.data` payload to the caller of DQEVENT. This proves only a generic kernel-side route. It does not establish that QuickCamera opens this node, subscribes to CRM type/id 0 with event ID 0 or 2, dequeues it, or transforms its payload into CSLMessageHandler's distinct envelope.

The distinct cam_req_mgr_event_data structure contains session_hdl, link_hdl, frame_id, req_id, tv_sec, tv_usec and has no role in the traced cam_req_mgr_notify_message path. The queued SOF events carry cam_req_mgr_message in v4l2_event.u.data; these structures must not be conflated.

## 3. AArch64 ABI layout

The check used NDK Clang 18.0.3 with target aarch64-linux-android29, but included the exact pinned Phoenix UAPI videodev2.h, types.h, ioctl.h, media.h, v4l2-controls.h, v4l2-common.h, plus the exact pinned cam_req_mgr.h and cam_defs.h. A local compile-only shim defines kernel annotation macros only; it does not replace any struct or field declaration. A C static-assert harness verified sizes, alignments and offsets; clang exited 0.

| Type | AArch64 size/alignment | Field offsets (relative to type) |
|---|---|---|
| cam_req_mgr_event_data | 40 / 8 | session_hdl=0, link_hdl=4, frame_id=8, reserved=12, req_id=16, tv_sec=24, tv_usec=32 |
| cam_req_mgr_frame_msg | 40 / 8 | request_id=0, frame_id=8, timestamp=16, link_hdl=24, sof_status=28, frame_id_meta=32, reserved=36 |
| cam_req_mgr_custom_msg | 48 / 8 | custom_type=0, padding to request_id=8, frame_id=16, timestamp=24, link_hdl=32, custom_data=40 |
| cam_req_mgr_message | 56 / 8 | session_hdl=0, reserved=4, union u=8; therefore frame request_id=8, frame_id=16, timestamp=24 |
| Pinned v4l2_event | 136 / 8 | u.data=8 (64 bytes), pending=72, sequence=76, timestamp=80, id=96, reserved=100 |

The CRM message fits in the 64-byte V4L2 event data area. Its frame request ID and timestamp are at relative offsets +0x08 and +0x18 from the data-area/message base.

## 4. Independent QuickCamera comparison

The local proprietary quickcamera.core.so SHA-256 is fb22355acd35b9772a5538a7d1c49175641165ad0368e7c47e5831f5f1727017. A bounded local disassembly review of CSLMessageHandler at 0x375d0–0x37724 reconfirmed: it reads a 32-bit message type at +0x00, a 64-bit request ID at +0x08, and a 64-bit value at +0x18, which it stores in a 38-entry ring. The existing P3-A3 proof also establishes the previous-ring-slot timeout fallback; this task neither observes its runtime occurrence nor infers one.

The two 64-bit subfield offsets exactly match cam_req_mgr_message.u.frame_msg from the pinned source. But the outer layouts differ: CRM starts with session_hdl at +0x00 and reserved at +0x04; QuickCamera treats +0x00 as a message type. CRM’s SOF-vs-BOOT_TS discriminator is the outer V4L2 event ID, not a cam_req_mgr_message type field. No code/dataflow was found that transforms, wraps, or passes the kernel message into this QuickCamera message.

In the available SHA-pinned QuickCamera ELF, the dynamic symbol table does not expose a direct ioctl import, and bounded string inspection found no VIDIOC_SUBSCRIBE_EVENT, VIDIOC_DQEVENT, cam-req-mgr, or CRM SOF event names. This does not prove no other library or service subscribes: dependencies and the complete Pico userspace stack were not available as source or binaries here. Userspace subscription/dequeue/dispatch and event identity therefore remain BLOCKED. No proprietary ELF or disassembly was included in the evidence archive or report.
