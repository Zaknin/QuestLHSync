## 4. Engineering conclusion and minimum remaining evidence

### 1. Kernel SOF → QuickCamera CSL timestamp identity

Minimum static evidence: the pinned source tree and hashes for the listed files; a matching running-build mapping; complete CSID timestamp creation and ISP/CRM event construction; exact event payload ABI; and a consumer path that demonstrably transports the same value into the QuickCamera CSL message. If the kernel-to-CSL bridge crosses an opaque vendor library or device interface, exact call/dataflow evidence for that bridge is still required. No runtime hook is justified before this source pass.

### 2. Request/frame ID correlation

Minimum evidence: source-level assignment and propagation for CRM request ID and frame ID, plus the receiving CSL message's documented field semantics. Then, if the software path does not guarantee a one-to-one relation, a separately approved numeric-only runtime sample pairing CRM/CSL identifiers to PVR metadata is needed. Matching counters or timestamps alone are insufficient.

### 3. Runtime fallback occurrence

Static analysis already establishes that the fallback branch exists and can use a previous ring slot. Runtime occurrence and frequency remain unknown. The minimum useful evidence is an existing, non-invasive diagnostic that explicitly identifies timestamp source request ID/fallback selection for the same output metadata. If no such diagnostic exists, instrumentation would be a distinct behavior/timing risk and should be proposed only after the exact source-to-sink gap is documented and the expected information gain reviewed; no hook or instrumentation is proposed in this audit.

### 4. Timestamp suitability for Lighthouse synchronization

Minimum evidence: the exact build-matched clock scale/domain and event semantics; a verified mapping from the timestamp to the same frame/request; clock relation and uncertainty against the Android monotonic/delivery domain; and authoritative sensor semantics defining whether the timestamp corresponds to physical SOF, exposure start, midpoint or another point. If source semantics do not settle the physical event, a separately approved optical-reference experiment is required. Kernel delivery latency or a QTIMER-like label is not exposure time.

### Recommendation

The highest-value next step is **targeted acquisition of only the six named source files and enough version/config metadata for the pinned commit**, once an offline source copy is available or source retrieval is separately permitted. Do not repeat M2 node inventory for this purpose. Do not start SOF runtime instrumentation: source provenance and the kernel-to-CSL bridge are currently the dominant blockers. A hardware experiment is not yet justified. If matching source or build mapping cannot be obtained, keep this branch `BLOCKED` rather than extending the investigation with unrelated runtime collection.

All safety gates remain false: `exact_time=false`, `mapping_verified=false`, `pose_verified=false`, `shared_buffer_identity_verified=false`, `frame_meta_bridge_verified=false`, `live_lighthouse_correction_allowed=false`, `physical_event_verified=false`.
