## Result

**Overall: PARTIAL.** The specified public CamX revision contains a complete CRM V4L2 event to `CSLMessage` callback path. Its AArch64 `CSLMessage` has request and timestamp fields at offsets `+0x08` and `+0x18`, matching the fields read by the SHA-pinned Pico QuickCamera binary. The Pico binary also declares `camx_core.so` as a direct dependency and registers its own `CamQuickAccessDevice::CSLMessageHandler` callback.

This is stronger than offset/name similarity, but it is not the missing Pico-specific proof: the matching SHA-pinned `camx_core.so` artifact is absent from the existing private artifact set. The public CamX source's relation to that binary and its applicability to the reported Pico firmware are unestablished. The exact kernel CRM event → Pico QuickCamera CSL callback identity therefore remains **BLOCKED**; runtime occurrence was **NOT OBSERVED**. No timing, mapping, physical-event, or Lighthouse gate is promoted.

## Public CamX source contract — verified only for this revision

### Device, subscription, poll and dequeue

`CSLHwEnumerateAndAddCSLHwDevice` (`camxcslhwinternal.cpp:2073-2144`) opens `/dev/mediaN`, obtains media-device information, enumerates entities, and constructs `/dev/<entity.name>` for the selected entity. For a request-manager/VNODE entity, `CSLHwAddKMDPrivateDeviceToInstance` (`1563-1578`, `1624-1651`) opens that supplied path with `O_RDWR | O_NONBLOCK`, retains its fd, and subscribes on it. This source does not hard-code a `/dev/videoN`; the concrete request-manager node depends on the enumerated media entity.

`CSLHwInternalDefaultSubscribeEvents` (`1003-1013`) fills `v4l2_event_subscription.id` and `.type` and invokes `VIDIOC_SUBSCRIBE_EVENT`. The default operation (`3139-3180`) reaches `ioctl(pDevice->fd, request, pArg)` directly. It does not route these event ioctls through `CSLHwInternalDefaultIoctl2` or wrap them in `VIDIOC_CAM_CONTROL`. The polling thread (`1385-1417`) includes the retained fd, waits with `poll`, then `CSLHwInternalDQEvent` (`1048-1067`) calls `ioctl(fileDes, VIDIOC_DQEVENT, pEvent)` directly. Successful events with type `V4L_EVENT_CAM_REQ_MGR_EVENT` proceed to the CRM dispatcher.

### CRM payload to CSL message and callback

`CSLHwInternalSendRequestManagerEvent` (`1147-1296`) interprets `v4l2_event.u.data` as `cam_req_mgr_message`. `CSLHwFindPipelineIndex` (`1081-1135`) uses the message session handle and the frame link handle to select the registered per-link callback. For a `V4L_EVENT_CAM_REQ_MGR_SOF_BOOT_TS` event, the bridge copies `request_id`, `frame_id`, `timestamp`, and `link_hdl` into `CSLFrameMessage`, sets `timestampType = CSLTimestampTypeMono` and `bNotify = TRUE`. For `V4L_EVENT_CAM_REQ_MGR_SOF`, it copies the same payload fields, sets `timestampType = CSLTimestampTypeQtimer` and `bNotify = FALSE`. The timestamp value is copied unchanged at this bridge; there is no conversion in this function.

The constructed `CSLMessage` is delivered by calling the selected per-link `messageHandler`. `Pipeline::StreamOn` (`camxpipeline.cpp:683-697`) registers `Pipeline::CSLMessageHandler` after linking a real-time pipeline; the handler is at `3407-3530`. The public source therefore provides the full callback mechanism for its own implementation.

There is a request-ID-zero filter before pipeline lookup: ID zero is ignored for events other than SOF and ERROR. Thus a zero-ID BOOT_TS event is discarded by this source, whereas SOF ID zero is allowed onward. `CSLFrameMessage` documents zero as “no request”; the pipeline handler, however, indexes `m_pCSLSyncIDToRequestId` using `requestID % capacity` and then applies its `CamxInvalidRequestId` sentinel check. It does not have a separate explicit `requestID == 0` guard there. The resulting mapped value for zero depends on that table slot and sentinel semantics; it must not be presumed to stay zero or to identify a real request.

### QTIMER, BOOT_TS, `timestampType` and `bNotify`

For this source revision, SOF maps to the Qtimer marker with notification false; SOF_BOOT_TS maps to the Mono/boot-time marker with notification true. The source bridge copies the event timestamp and assigns the marker; it does not itself convert QTIMER or BOOTTIME. In the separate pinned Phoenix kernel source discussed in M2.5, the online CSID path converts 19.2 MHz QTIMER ticks to nanoseconds and derives a BOOTTIME value; the CamX bridge would preserve the selected event's value. These are separate public source revisions with no build mapping tying them together or to Pico. Do not read `CSLTimestampTypeQtimer` as proof that the copied Pico value is raw ticks or a physical SOF time.

In `Pipeline::CSLMessageHandler`, the original timestamp and frame count are first copied to `timestampInfo`. The CSL sync ID is translated to the pipeline request ID by a bounded modulo table populated in `ProcessRequest` (`camxpipeline.cpp:1268-1270`) from `CaptureRequest::CSLSyncID` to `CaptureRequest::requestId`; `OpenRequest` (`1119-1164`) submits that sync ID to `CSLOpenRequest`. Therefore IDs crossing CSL and pipeline interfaces are deliberately not assumed equal. For Qtimer messages the original timestamp is published through a vendor-tag payload. When `bNotify` is true, the source calls the SOF notification path, then may replace `pMessage->frameMessage.timestamp` with `PropertyIDSensorExposureStartTime` metadata before the shutter notification. When `bNotify` is false it follows the recovery-check path. Arrival time is explicitly not a reliable event time in the public header.

## AArch64 `CSLMessage` ABI

An NDK Clang++ compile-only check used the exact pinned `camxcsl.h` and `camxtypes.h`, target `aarch64-linux-android29`, and `static_assert` checks for sizes, alignments and offsets. It passed.

| Type/field | AArch64 offset / size |
|---|---:|
| `CSLFrameMessage` | size 40, alignment 8 |
| `CSLFrameMessage.requestID` / `frameCount` / `timestamp` | 0 / 8 / 16 |
| `CSLFrameMessage.link_hdl` / `timestampType` / `bNotify` | 24 / 28 / 32 |
| `CSLErrorMessage` | size 40, alignment 8 |
| `CSLMessage.type` / union `message` | 0 / 8 |
| `CSLMessage.message.frameMessage.requestID` | `+0x08` |
| `CSLMessage.message.frameMessage.frameCount` | `+0x10` |
| `CSLMessage.message.frameMessage.timestamp` | `+0x18` |
| `CSLMessage.message.frameMessage.link_hdl` / `timestampType` / `bNotify` | `+0x20` / `+0x24` / `+0x28` |
| `CSLMessage` | size 48, alignment 8 |

This validates the layout of the public source revision. It is not an assertion about a Pico provider binary. The Pico QuickCamera instruction reads at `+0x08`, `+0x18`, `+0x24`, and `+0x28` are structurally compatible with this public ABI.

## Exact evidence still needed

The narrow missing binary dependency is a SHA-verified Pico `camx_core.so` from the same reported firmware build, with its original partition path, ELF Build ID, and a build mapping tying it to `Pico/Phoenix_ovs/PICOA8110:10/5.11.2/smartcm.1725996131:user/dev-keys` / `4.19.81-perf+`. Its static imports/exports and instructions must show: (1) the implementation resolving QuickCamera's `CSLRegisterMessageHandler`; (2) CRM V4L2 subscription on the media-entity node; (3) direct/preserving DQEVENT payload handling; (4) the CRM-to-CSL field writes and the call through the registered callback pointer. Exact handler identity requires the source/binary call chain to meet at the relocated `CamQuickAccessDevice::CSLMessageHandler` pointer already proven in QuickCamera. A runtime linker map would establish which installed path actually supplied the dependency, but no such runtime observation was made or attempted here.

Even that static bridge would not show that the event occurred in a particular run, which timestamp path was selected, that fallback occurred, or that the event marks physical exposure start. Those require separately authorized evidence specific to those claims; no instrumentation is justified by this source-only result.
