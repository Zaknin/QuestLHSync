## Outcome

The one owner-authorized, read-only attempt verified the target software fingerprint and ABI, then stopped at the fixed shell-v2 framing check. It did **not** run the logcat capability query or callback-log snapshot. Runtime process existence and callback occurrence are therefore **NOT OBSERVED / NOT EVALUABLE**, not absent. No retry was made.

The archived manifest records `ADB_TRANSPORT_BLOCKED` and `SHELL_PROTOCOL_V2_UNVERIFIED`. Offline control-flow review established that execution reached the marker validator only after the shell command returned the expected status 23, with zero stderr bytes. The marker validator then rejected stdout. The specific byte difference is unavailable because raw stdout was not retained; CRLF is one possible cause, not a confirmed cause. The audited classification is `OUTPUT_FRAMING_BLOCKED / SHELL_V2_MARKER_MISMATCH`, rather than a demonstrated ADB transport failure. The original private manifest and archive are preserved unchanged.

## Scope and safety

M2.8D was limited to one existing-default-log observation design for the static QuickCamera callback-specific record. No camera, tracking, SteamVR, Lighthouse, `/proc`, root, process memory, tracing, hook, APK, logging property or logging level was touched. The fixed target was selected by the existing digest-bound process-local environment variable; no `adb devices`, endpoint scan, or alternate-device selection was used. No approval record was created. The direct owner authorization is contextual and is not authentication.

The collector bounds a run to 15 seconds, 40 protocol records, 16 candidate processes, six ADB invocations and 64 KiB combined host output. ADB is invoked using the pinned SDK executable, exact argv vectors and `shell -T sh -s` with only one of three fixed checked-in scripts on stdin. Stdout and stderr are drained separately; only stdout is retained in memory and stderr is reduced to a byte count. Raw process-table and logcat lines are never intentionally emitted by the remote script; host evidence stores only allowlisted PID/name and numeric callback fields. Dry-run makes no ADB call.

The capability probe uses `logcat -b main -d -v threadtime -t 1` and discards both streams on-device. Android 10 AOSP defines `-t <count>` as a request for the most recent records and treats zero as invalid, warning and falling back to one; therefore `-t 1` is used as the bounded option check ([Android 10 `logcat.cpp`](https://android.googlesource.com/platform/system/core/%2B/refs/tags/android-10.0.0_r47/logcat/logcat.cpp)). This source establishes AOSP behavior for that revision, not the installed PICO Toybox implementation.

## Static record and field interpretation

The only selected callback-specific pattern is the pinned QuickCamera INFO format `CSLTimestampTypeQtimer frameMessage:requestID=..., linkhdl=..., frameCount=..., timestamp=..., monoTimestamp=...` at `quickcamera.core.so` offset `0x193e0`, reached from `CSLMessageHandler` around `0x37724` under the message-type/timestamp-type and logging gates documented in the M2.8C report. Presence of this string or callsite is not runtime emission.

The M2.8C offset audit establishes the variadic field flow: `requestID` is loaded from `CSLMessage+0x08`; `frameCount` is the signed 64-bit word at `+0x10`; `timestamp` is `+0x18`; `linkhdl` is `+0x20`; and the `monoTimestamp` argument is reloaded from the request-ID-indexed ring slot. The provider binary statically copies CRM `frame_id` into `CSLMessage+0x10`, so that is the source-level meaning of this logger's `frameCount` value on the traced bridge. It is **not** evidence that CRM, CSL, pipeline, PVR and `FrameMetaDate` identifiers share one namespace. The parser was corrected to validate `frameCount` as signed 64-bit, matching the `%lld` format and the field width; boundary and overflow regressions cover this.

The logged `monoTimestamp` is not an independent Android monotonic-clock sample: the straight-line path reads the same request-indexed 38-slot ring value that is populated from the message timestamp, subject to concurrency. The format does not log CRM event ID, `timestampType`, `bNotify`, a fallback marker, or a physical sensor timestamp. Even a future matching record could support callback-specific logger execution and its logged fields only; it would not prove runtime provider byte identity, CRM event 0 versus 2, timestamp units/epoch/domain, fallback occurrence, PVR metadata correlation, physical SOF/exposure start, or Lighthouse suitability.

The original package was not changed or republished. Keep its recorded status intact; this report adds the offline diagnosis without rewriting private evidence.

## Result classes

| Status | Meaning |
|---|---|
| `CALLBACK_LOG_OBSERVED` | At least one allowlisted callback-specific record passed the host parser and is attributed to an accepted process row. |
| `NO_MATCHING_LOG_RECORDS_OBSERVED` | A valid bounded snapshot completed without a matching callback row, or no target process row was present. It is a snapshot-window result only. |
| `LOGCAT_CAPABILITY_BLOCKED` | The bounded option check failed or the fixed logcat option was unsupported. |
| `REMOTE_FILTER_BLOCKED` | The fixed script/helper did not establish its allowlisted on-device filtering contract. |
| `OUTPUT_FRAMING_BLOCKED` | A marker, protocol record, byte/line limit, or framing validation failed. M2.8D's hardware attempt belongs here after offline reclassification. |
| `ADB_TRANSPORT_BLOCKED` | The pinned executable, target, identity, ADB command, timeout, or remote status did not satisfy the expected transport contract before a more specific post-command framing failure. |

The archived manifest remains a faithful record of what the pre-correction executable emitted; this table gives the current audited interpretation, not a rewritten hardware artifact.
