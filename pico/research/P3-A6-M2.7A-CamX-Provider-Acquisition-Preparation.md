## Purpose and boundary

This change prepares a new, separately scoped, read-only runner for acquiring the actual `camx_core.so` provider candidates present on the owner-confirmed Pico 4 Pro build. It does not use a public Qualcomm implementation as a substitute. Provider bytes are needed to inspect the implementation behind `CSLRegisterMessageHandler`, CRM event subscription/dequeue, and CRM-to-CSL dispatch.

## Prepared implementation

New runner: [`p3a_m27b_camx_provider.py`](../tools/p3a_m27b_camx_provider.py). It is independent of the M1 and M2 PowerShell collectors and reuses P3-A’s archive builder and canonical publisher. Import and `--dry-run` are device-free.

The only accepted action is `read-only-camx-core-provider-acquisition`. A future execution requires a fresh P3-A6 approval with that exact action, owner-confirmed `Pico 4 Pro` target, UTC validity window, and limits no greater than 60 seconds and 200 command observations. The runner also imposes a 60-second runtime, 200 ADB-call observation, 160-command, 16-candidate, 64 MiB per-file, 128 MiB aggregate transfer, and 64 KiB ADB-stdout ceiling. Exact lowercase interactive `yes` is required after displaying the scope. It is an accident-prevention step, not authentication. The common Python execution gate is checked immediately before every ADB invocation.

The pinned executable is `$env:LOCALAPPDATA\Android\Sdk\platform-tools\adb.exe`; no PATH search or `adb devices` enumeration occurs. Exactly one explicit `--serial` or positive numeric `--transport-id` is required. The allowlist accepts only these argument-vector shapes after that selector:

```text
get-state
shell getprop <one of the six fixed identity keys>
shell sh -c <exact SHA-pinned fixed POSIX discovery script>
shell readlink -f <candidate path observed by that probe>
shell wc -c <resolved candidate source path observed by that probe>
shell sha256sum <resolved candidate source path observed by that probe>
pull <resolved candidate source path observed by that probe> <fixed ephemeral local destination>
```

No `su`, root, arbitrary shell command, command substitution, user-supplied path, file write to the device, or fallback command is accepted. ADB stdout is drained with a fixed byte ceiling; timeout, output overflow, nonzero exit, or malformed output stops the run and does not become an empty success.

## Discovery and candidate rules

The fixed probe recursively searches only these existing library roots: `/vendor`, `/system`, `/odm`, `/product`, `/system_ext`, and `/apex`. It finds actual entries named `camx_core.so`; it does not guess one partition path. It records each observed alias and resolved source path. Symlink targets must resolve to a library under an allowed root and a `lib64` path. Unresolved, out-of-root, wrong-path, and non-regular entries become explicit limitations and are not pulled. Candidate paths pass strict ASCII segment, traversal, and protocol framing validation.

The production discovery script SHA-256 in this prepared revision is `2bf7c8c6c799574a3787874af99c0f96806b8cba8bf4e19fd41802420b9b3010`; the runner computes and records it at runtime so any script change alters the reported digest.

Up to 16 candidates are retained. If a seventeenth candidate is observed, discovery is blocked before extraction; the runner does not select a subset by filesystem order. All candidates are retained for a normal bounded run. A source scan that is inaccessible or incompatible remains partial/blocked; it is never represented as an empty successful inventory.

Before any pull, the runner obtains and validates the exact owner-bound product tuple, fingerprint, and `arm64-v8a` ABI. It obtains the byte size for every candidate before transferring any candidate. If any file exceeds 64 MiB or the combined planned transfer exceeds 128 MiB, no candidate is pulled. For each candidate selected for transfer, it then rechecks fingerprint/ABI and symlink resolution, records remote SHA-256 before the pull, compares the downloaded file’s size and SHA-256, validates ELF64/AArch64, rechecks the resolved path and remote SHA-256 after the pull, and only then records the staged file.

Expected software identity:

```text
ro.product.model        A8110
ro.product.device       PICOA8110
ro.product.name         Phoenix_ovs
ro.product.manufacturer Pico
ro.build.fingerprint    Pico/Phoenix_ovs/PICOA8110:10/5.11.2/smartcm.1725996131:user/dev-keys

```

This is an owner-bound software identity check, not cryptographic attestation. The owner-confirmed Pico 4 Pro / international Pico OS fact remains established project context and is not inferred from `A8110` alone.

## Evidence and publication

Each private manifest records UTC creation time, action and approval association, build identity, source and resolved paths, source-root statuses, candidate limitations, collection status, exact methods, runner/probe SHA-256, per-candidate remote-before/local/remote-after SHA-256, byte size, ELF class/machine, Build ID, dynamic exported and undefined symbols, `DT_NEEDED`, and a locator list for relevant bridge symbol names. It does not save serials, raw shell output, unrelated system paths/logs, images, video, sensor data, process data, or memory.

The private ZIP includes only verified ELF files plus the diagnostic manifest. A valid, partial, or blocked package is sent only through the existing canonical publisher to the project’s private canonical P3-A SMB location. The physical share path remains in local project configuration rather than this public preparation report.

The publisher writes `.part` files exclusively, verifies read-back SHA-256, atomically finalizes the archive and manifest, then publishes the `.sha256` sidecar last. It rejects unsafe package names and any existing final or `.part` path, so a name collision cannot overwrite an earlier publication. If a publication step fails, it removes only `.part` files created by that call; it never removes previously published files. No receipt is returned before final sidecar read-back succeeds. The runner has no Google Drive or local persistent fallback; local ELF staging is temporary and removed on exit. The M2.6 canonical archive is not changed or republished by this task. Canonical publication was not attempted in M2.7A.

`PACKAGE_READY` means all discovered candidates were acquired and verified under these checks. It does **not** mean a candidate is runtime loaded, implements the public CamX source, receives a particular V4L2 event, or bridges a kernel SOF to the QuickCamera callback. Build ID, exports, undefined symbols, `DT_NEEDED`, and symbol hits are evidence for targeted static analysis only. A matching function name by itself does not prove a complete bridge.

## Android compatibility and residual limits

The generated script passed `/bin/sh -n` and executable WSL `/bin/sh` fixtures. That does not verify the exact Android 10/PICO Toybox behavior, SELinux access, permissions, `readlink -f`, recursive `find`, `wc -c`, `sha256sum`, or the remote argument reconstruction performed by a real ADB client. There are deliberately no compatibility fallbacks. Any unsupported command or output format stops safely and should be recorded as `BLOCKED` or `PARTIAL`; do not broaden the allowlist during a hardware session.

Discovery walks multiple roots and can take time. Its ADB call is subject to the remaining 60-second limit and stdout cap; a timeout or cap is a partial/blocked result, not proof no provider exists. A candidate hidden by Android permissions cannot be ruled out. `adb pull` reads only an observed candidate and runs unprivileged, but its effect on system load has not been measured. Byte limits cap host staging and archive size, not scan work. The 60-second deadline and per-call timeout are the primary scan bounds.

No runtime-loaded provider is established by this workflow. A runtime linker map or process memory read is outside scope and would need a separate review. No camera activation, device mutation, root, SELinux change, ioctl, tracing, ptrace, instrumentation, or Lighthouse action is needed for the proposed acquisition.
