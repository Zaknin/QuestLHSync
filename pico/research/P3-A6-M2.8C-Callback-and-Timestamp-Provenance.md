## Scope and safety

The offline phase used only the previously acquired, SHA-pinned `camx_core.so`, `quickcamera.core.so`, and QuickCamera HIDL implementation. It did not read `/proc`, retry M2.8B maps/FD methods, open a camera, start tracking/SteamVR, change Android logging, use root, or enable Lighthouse correction.

Offline analysis identified one callback-specific default-level diagnostic pattern, so one bounded read-only logcat snapshot was attempted after the pinned SDK ADB target returned `device` and all six owner-bound software-identity/ABI fields matched. The historical report records probe SHA-256 `7acf8c21df035a0a950519d11a39120c008e1462cf47fde2bbbf5ca326bc242b`; the bytes are unavailable here, so that script hash and implementation cannot be independently reproduced. The reported invocation requested only the `main` buffer, `-d`, `-v threadtime`, and the last 256 records, then attempted on-device PID/name and literal-message filtering. The host received 3,540 bytes, but its framing guard rejected the response. No normalized process or event record was accepted. Raw response bytes were not written to disk or included in either canonical package. Since framing failed, it is **unknown** whether the response consisted solely of normalized protocol records; filter-before-transfer was not established. No second logcat snapshot was run.

The identity check matched model `A8110`, device `PICOA8110`, name `Phoenix_ovs`, manufacturer `Pico`, fingerprint `Pico/Phoenix_ovs/PICOA8110:10/5.11.2/smartcm.1725996131:user/dev-keys`, and ABI `arm64-v8a`. ## Offline log feasibility

### QuickCamera callback-specific record

The QuickCamera binary contains the exact format string at file/virtual offset `0x193e0`:

```text
[ INFO]%s %s:653 %s() DevIns:%p CSLTimestampTypeQtimer frameMessage:requestID=%lld, linkhdl:%p, frameCount=%lld, timestamp=%lld, monoTimestamp=%lld
```

The pinned callback registration evidence remains: callsite `0x37d14`, relocation slot `0x4f680` → veneer `0x4c470` → handler entry `0x375d0`. In the bounded handler window, the log call is at `0x37724`, through `CamX::Log::LogSystem`; its format names `CSLMessageHandler`. The literal format contains an `INFO` label, and a `[CORE]` component marker is passed; the actual Android logcat priority was not observed. The Android logcat tag is not recoverable from this callsite alone. The provider ELF also imports Android `liblog` entry points, but that does not by itself prove this particular message reached logcat.

The message path is conditional: the handler accepts message type 0 for this branch and checks the timestamp-type word at `CSLMessage+0x24`; nonzero branches away before this log. At `0x376b4`, `ldp x9,x10,[x20,#0x8]` loads request ID from `+0x08` and the 64-bit word at `+0x10`. At `0x376d8`, `ldr w8,[x20,#0x20]` loads the low 32 bits of the word at `+0x20`; `0x376dc` loads timestamp from `+0x18`. The format pointer in `x3` is `0x193e0`; `x4–x7` carry the format's first four variadic arguments, with `x7=x19` for `DevIns:%p`. At `0x37714–0x37720`, stack arguments are stored in reverse instruction order but consumed in format order: request ID from `+0x08`, the `+0x20` word for `linkhdl:%p`, the `+0x10` word for `frameCount=%lld`, timestamp from `+0x18`, and the modulo-38 ring value for `monoTimestamp`. The earlier reading that `frameCount` came from `+0x20` confused load order with variadic argument order and is corrected here.

The pinned provider report says CRM `frame_id` is copied to `CSLMessage+0x10`, timestamp to `+0x18`, and link data to `+0x20`. The QuickCamera logger passes `+0x10` as its `frameCount` value and `+0x20` as its `linkhdl` value. Thus the static byte flow supports that the provider's frame-ID word is the value formatted under the QuickCamera `frameCount` label for this bridge. This is a static field-flow conclusion only: it does not establish runtime callback delivery, a live CRM/PVR join, or that another pipeline's frame counter uses the same namespace. The `bNotify` word at `+0x28` is not included in this log record and is loaded only after the log call.

At `0x37640` the message timestamp is written to the request-ID modulo-38 ring; at `0x376e0` the same request-indexed ring slot is reloaded for `monoTimestamp` (subject to concurrent interference). That label is not evidence that an Android monotonic API was sampled. The log site is gated by the `g_logInfo` word's bit `0x10` or a nonzero `g_logInfoUpdated` word (`0x37688–0x376a4`); neither gate was changed. The `bNotify` read at `+0x28` occurs after the log call and does not gate this log site.

If a well-framed record were observed with a PID attributable to a matching live QuickCamera/PVR process, it would be direct evidence that a code path containing this callback-specific log site reached its logger. It would not independently prove that the runtime-loaded library was byte-identical to this pinned ELF, because M2.8B could not read process mappings.

## Recommendation and gates

The highest-value next work is offline-only: split the host parser's framing diagnostics into exact line-count/control-character reasons, add CRLF-at-line-boundary and 40-record tests, and verify the exact remote argument/serialization path with synthetic output without retaining raw logs. The single M2.8C logcat attempt is spent. Do not repeat it in this phase. Any later snapshot must first demonstrate that only the normalized allowlist can cross the ADB boundary; if that cannot be proven, stop without device collection.

This result does not change the M2.8B `PROC_ACCESS_DENIED` outcome and does not justify another `/proc` method. Runtime-loaded provider identity, separate SOF/BOOT_TS event identity, request/frame joins, fallback occurrence, timestamp units/domain, physical SOF/exposure timing, and Lighthouse suitability remain unproven.

## M2.8C-R offline framing recovery (2026-10-19)

### Source provenance

The published M2.8C baseline contained documentation only for this collector. No original Python parser/runner, fixed POSIX probe, synthetic test, or WSL fixture was recovered. The following new files are **reconstructed from the documented contract**, not recovered originals:

- `pico/tools/p3a_m28c_logcat.py` — offline parser, safe error metadata, and inspectable ADB argv; its RFC 5737 target is inert test data and it has no ADB executor.

No ADB, Pico, or logcat command was run in M2.8C-R. The historical `BLOCKED_OUTPUT_FRAMING` remains unchanged and its exact cause is `UNKNOWN`; raw response bytes and the prior parser's guard state remain unavailable.

### Reconstructed diagnostic classes and output contract

The host parser returns only `error_code`, `byte_count`, `record_count`, and optional `line_number`/`offset` on failure. It does not echo malformed bytes, lines, process values, or stderr. The error vocabulary is:

| Code | Trigger in reconstructed implementation |
|---|---|
| `OUTPUT_LINE_LIMIT` | More than 40 newline-terminated protocol records, or remote normalized rows would exceed 40 |
| `INVALID_CONTROL_CHARACTER` | A protocol line contains a control byte other than tab |
| `INVALID_LINE_ENDING` | A standalone/embedded CR remains after optional CRLF normalization at the record boundary |
| `MALFORMED_PROTOCOL_RECORD` | Invalid envelope, field count/order, process/event schema, character set, or numeric range |
| `MISSING_PROTOCOL_TERMINATOR` | Missing final newline, END record, or remote status sentinel |
| `OUTPUT_TRUNCATED` | More than 64 KiB at host boundary or a raw logcat line exceeds the 4,096-byte processing bound |
| `REMOTE_FILTER_UNVERIFIED` | Process list/filter attestation is malformed or outside its fixed contract |
| `LOGCAT_UNSUPPORTED_OPTION` | A bounded allowlisted unsupported-option phrase appears in the separately captured stderr channel |
| `REMOTE_COMMAND_FAILURE` | `ps`, logcat, remote awk, or the remote shell fails without a more specific safe classification |

The reconstructed script invokes only `ps -A -o PID,NAME` and `logcat -b main -d -v threadtime -t 256`. It first selects at most 16 validated process rows, then filters logcat lines by a fixed literal marker and those PIDs. Host stdout contains only a fixed protocol envelope and validated PID/name, date/time, numeric request/frame/timestamp fields, and a constant source label. Raw logcat stdout is buffered in the remote AWK process and never emitted; on nonzero logcat status the buffered event rows are discarded. Remote stderr remains a separate ADB stderr stream; the host parser classifies it in memory and returns only safe metadata. The Python module itself does not execute ADB or persist either stream.

The generated remote script SHA-256 is recorded by the tests and recomputed from the checked-in script at import. This proves the reconstructed local source/hash pairing, not identity with the lost original script or with any script previously sent to the device.

## M2.8D follow-up — `frameCount` parser width and marker stop (2026-10-20)

The registered QuickCamera handler's INFO format uses `%lld` for `frameCount`. The audited AArch64 argument flow passes the 64-bit `CSLMessage+0x10` word to that placeholder; `+0x20` is passed to `linkhdl`, not frame count. The acquired provider statically copies its CRM `frame_id` field into `+0x10`. The M2.8D parser was therefore corrected from unsigned 32-bit validation to signed 64-bit range validation and covered at both signed boundaries and one value beyond each boundary. This aligns parsing to the logger's format and field width; it does not establish identifier equality between CRM, CSL, pipeline, PVR, or `FrameMetaDate` namespaces.

The single M2.8D hardware attempt verified fingerprint/ABI and returned from the shell-v2 call with expected exit status 23 and zero stderr, then failed exact marker validation. It never reached logcat capability or snapshot. The old manifest records generic `ADB_TRANSPORT_BLOCKED/SHELL_PROTOCOL_V2_UNVERIFIED`; raw stdout is absent, so CRLF remains only a hypothesis. The offline parser now accepts only LF or CRLF as the marker line ending and reports `OUTPUT_FRAMING_BLOCKED / SHELL_V2_MARKER_MISMATCH` for a rejected marker after the expected process result. No log row or callback presence/absence was observed. See [`P3-A6-M2.8D-Callback-Log-Verification.md`](P3-A6-M2.8D-Callback-Log-Verification.md). All clock-domain, event-ID, fallback, physical-SOF/exposure and Lighthouse conclusions remain unchanged and unproven.
