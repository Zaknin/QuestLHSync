**Date:** 2026-10-19

**Outcome:** `BLOCKED_OUTPUT_FRAMING`; callback evidence was not evaluable

## Scope and safety

The offline phase used only the previously acquired, SHA-pinned `camx_core.so`, `quickcamera.core.so`, and QuickCamera HIDL implementation. It did not read `/proc`, retry M2.8B maps/FD methods, open a camera, start tracking/SteamVR, change Android logging, use root, or enable Lighthouse correction.

Offline analysis identified one callback-specific default-level diagnostic pattern, so one bounded read-only logcat snapshot was attempted after the pinned SDK ADB target returned `device` and all six owner-bound software-identity/ABI fields matched. The attempt used one fixed probe SHA-256 `7acf8c21df035a0a950519d11a39120c008e1462cf47fde2bbbf5ca326bc242b`; it requested only the `main` buffer, `-d`, `-v threadtime`, and the last 256 records, then attempted on-device PID/name and literal-message filtering. The host received 3,540 bytes, but its framing guard rejected the response. No normalized process or event record was accepted. Raw response bytes were not written to disk or included in either canonical package. Since framing failed, it is **unknown** whether the response consisted solely of normalized protocol records; filter-before-transfer was not established. No second logcat snapshot was run.

The identity check matched model `A8110`, device `PICOA8110`, name `Phoenix_ovs`, manufacturer `Pico`, fingerprint `Pico/Phoenix_ovs/PICOA8110:10/5.11.2/smartcm.1725996131:user/dev-keys`, and ABI `arm64-v8a`. This verifies the owner-bound software tuple for this attempt, not cryptographic device attestation.

## Offline log feasibility

### QuickCamera callback-specific record

The QuickCamera binary contains the exact format string at file/virtual offset `0x193e0`:

```text
[ INFO]%s %s:653 %s() DevIns:%p CSLTimestampTypeQtimer frameMessage:requestID=%lld, linkhdl:%p, frameCount=%lld, timestamp=%lld, monoTimestamp=%lld
```

The pinned callback registration evidence remains: callsite `0x37d14`, relocation slot `0x4f680` → veneer `0x4c470` → handler entry `0x375d0`. In the bounded handler window, the log call is at `0x37724`, through `CamX::Log::LogSystem`; its format names `CSLMessageHandler`. The literal format contains an `INFO` label, and a `[CORE]` component marker is passed; the actual Android logcat priority was not observed. The Android logcat tag is not recoverable from this callsite alone. The provider ELF also imports Android `liblog` entry points, but that does not by itself prove this particular message reached logcat.

The message path is conditional: the handler accepts message type 0 for this branch and checks the timestamp-type word at `CSLMessage+0x24`; nonzero branches away before this log. The code reads request ID at `+0x08`, timestamp at `+0x18`, and frame count at `+0x20`. It writes the timestamp to the request-ID modulo-38 ring and then reloads that same slot for the variadic `monoTimestamp` value. In this straight-line path the two values therefore come from the same message timestamp/ring slot (subject to concurrent interference); the second label is not evidence that an Android monotonic API was sampled. The `bNotify` word at `+0x28` is not included in this log record and is loaded only after the log call. Logging is also conditional on the binary's `g_logInfo` / `g_logInfoUpdated` gates; no setting was changed to force emission.

If a well-framed record were observed with a PID attributable to a matching live QuickCamera/PVR process, it would be direct evidence that a code path containing this callback-specific log site reached its logger. It would not independently prove that the runtime-loaded library was byte-identical to this pinned ELF, because M2.8B could not read process mappings.

## One bounded runtime attempt

The pinned SDK ADB executable was used with the fixed target binding. The attempt made 8 ADB commands: selected-transport state, six exact `getprop` identity/ABI reads, and one `shell sh -c` probe containing one `logcat` snapshot. Elapsed time was `0.436729` seconds. UTC window was `2026-10-19T18:52:31.754090+00:00` through `2026-10-19T18:52:32.190821+00:00`.

The host parser rejected the probe response as `OUTPUT_FRAMING`; the guard combined “more than 40 lines” and embedded-control checks, so the precise failing subcondition was not retained. `normalized_record_count=0` means no records passed the parser, **not** that no matching logs existed. Required logcat filter support is `NOT_CONFIRMED`; the ADB shell return code alone does not reveal the captured protocol status. No retry was made. No camera or tracking pipeline was activated, and no protected procfs interface was accessed.

### Canonical private evidence

The first publication, `p3a-m28c-callback-log-20261019T185232Z-a3440d0e`, was committed ZIP → manifest → `.sha256`; independent read-back confirmed the ZIP and manifest hashes against the sidecar. ZIP SHA-256: `90f464272f6e2072dab788d35e53aacfdc08dc0cc5e0fa847414ad36c76b5b65`; manifest SHA-256: `2e8608b5ee4f0a5ffe2c9edd831c91da857493b874adf5b987547c3ad261e1b5`. A caller-shape error caused the publisher receipt to raise after commit, and the first ZIP's embedded wrapper manifest did not byte-match its external manifest. The artifact was preserved unchanged.

The corrected diagnostic publication is `p3a-m28c-callback-log-correction-20261019T185417Z-44e09d65`. Its ZIP SHA-256 is `a2dbe15f34cb04fcaae848e3b482cab618fa478b8177e1362b9d2112480bc7b6`; external manifest SHA-256 is `04d2e4e30cbbf526dfb740e12a404d64ac6bc464936ba7641a9ac73faca634de`. Independent read-back verified the `.sha256` entries, ZIP integrity, a single manifest-only archive, and byte-identical embedded/external manifest. It contains only the actual identity/status/limit/script-hash metadata, `OUTPUT_FRAMING`, the 3,540-byte output length, and zero accepted normalized rows; it contains no raw log lines or proprietary ELF.

## Recommendation and gates

The highest-value next work is offline-only: split the host parser's framing diagnostics into exact line-count/control-character reasons, add CRLF-at-line-boundary and 40-record tests, and verify the exact remote argument/serialization path with synthetic output without retaining raw logs. The single M2.8C logcat attempt is spent. Do not repeat it in this phase. Any later snapshot must first demonstrate that only the normalized allowlist can cross the ADB boundary; if that cannot be proven, stop without device collection.

This result does not change the M2.8B `PROC_ACCESS_DENIED` outcome and does not justify another `/proc` method. Runtime-loaded provider identity, separate SOF/BOOT_TS event identity, request/frame joins, fallback occurrence, timestamp units/domain, physical SOF/exposure timing, and Lighthouse suitability remain unproven.
