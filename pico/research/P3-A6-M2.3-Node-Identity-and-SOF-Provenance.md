### New evidence behavior

Collector revision is now `P3-A6-M2-v3`, with private JSON evidence schema `p3a6.m2.node_inventory.v2`. Parser-created node objects carry the exact validated `videoN` token as `node_id`; that field is retained when node records are serialized into private evidence. The source key is copied as-is and is not inferred from array order or device number.

Sysfs field outcomes now use bounded codes:

| Code | Meaning |
|---|---|
| `OBSERVED` | One single-line value passed the existing character and length allowlist. |
| `ATTRIBUTE_MISSING` | The fixed attribute path was not present/resolvable at the read check. |
| `PERMISSION_DENIED` | The shell readability check or open was denied. This does not identify whether DAC or SELinux caused the denial. |
| `INVALID` | Empty, multiline, overlong, malformed, out-of-range, control-bearing or disallowed value. The value is cleared before output. |

Only fixed status tokens and an empty field value are emitted for failures; raw invalid or unreadable content is not saved. Before classifying a name as missing, the probe checks read/search access to the fixed parent directory and uses a fixed bracket-glob for the exact attribute name. A denied directory listing or path check is therefore not labeled missing; if a listed entry cannot be inspected/opened it is reported as denied (a dangling entry is invalid). Independent valid attributes remain in the record. Source-level `UNAVAILABLE`, `PERMISSION_DENIED`, `NOT_OBSERVED` and `LIMIT_REACHED` meanings remain distinct. A source can still be `OBSERVED` while one field is denied or invalid, and `metadata_fields_complete=false` prevents a complete inventory claim.

The bounded correlation summary groups both sources by numeric major. It marks a major group `AMBIGUOUS_BY_MAJOR` when multiple nodes occur in either source. An individual match is emitted only for one unique exact `major:minor` tuple on each side. Decimal major/minor formatting is normalized only for comparison; the original `videoN` identifiers remain unchanged. A shared major (such as major 81) is a group-level correspondence, not a unique node match. Even a unique exact tuple establishes only sysfs-to-`/dev` node metadata correspondence; it does not prove process ownership, a PVR file descriptor, ioctl attribution, queue use or frame delivery.

## B. Qualcomm SOF source audit

### Upstream Qualcomm source status

**BLOCKED: no matching Camera Request Manager header/source is present in the local project or searched `C:\Dev` source tree.** Local text search found no definitions/usages of `V4L_EVENT_CAM_REQ_MGR_SOF` or `V4L_EVENT_CAM_REQ_MGR_SOF_BOOT_TS`; no local `cam_req_mgr` source/header was found. No internet lookup was performed because this task is offline-only.

Consequently the following remain **unknown** for these named events: event numeric IDs, payload structure and field offsets, request/frame identifier semantics, units and clock domains, delivery/copy-out behavior, and header/kernel-version differences. No event contract or version compatibility can be asserted from this checkout.

The existing project note [`P2-Qualcomm-QTIMER-Camera2-References-20261016.md`](P2-Qualcomm-QTIMER-Camera2-References-20261016.md) contains a prior public-source citation to Qualcomm downstream `kernel/msm.git`, commit `0bdc64f155814eb6a109d0ec9e3965c821da5853`, file `cam_ife_csid_core.c`. That note summarizes a CSID implementation reading a SOF QTIMER, converting 19.2 MHz ticks and deriving a boot timestamp. This is a previously documented lead, not a source re-opened or version-matched in this task. It concerns a CSID implementation and does **not** establish either Camera Request Manager event payload or applicability to Pico OS.

### Pico-specific static evidence

These statements are from existing SHA-pinned Pico static research; no proprietary ELF or disassembly was copied into this report:

- [`P3-A4-Timestamp-Semantics.md`](P3-A4-Timestamp-Semantics.md) and [`P3-A3-CSL-Timestamp-SharedBuffer-20261017.md`](P3-A3-CSL-Timestamp-SharedBuffer-20261017.md) describe `quickcamera.core.so` (SHA-256 `fb22355acd35b9772a5538a7d1c49175641165ad0368e7c47e5831f5f1727017`). The traced `CSLMessageHandler` reads a request ID at message `+0x08` (`0x37608`) and a 64-bit value at `+0x18` (`0x37618`), then caches it using request modulo 38 (`0x37620..0x37640`). The diagnostic string labels a value `CSLTimestampTypeQtimer` and separately names `monoTimestamp`; its enum definition, units, epoch and event semantics were not recovered.
- The same analysis finds a `sof notify` string in the binary but no code/dataflow tying that string to the described message, ring value, Camera Request Manager event or physical sensor event. A string match is not event provenance.
- In the traced callback, the timestamp is written at metadata `+0` (`0x387f0..0x387fc` or timeout path `0x38c10..0x38c1c`), request ID at `+8` (`0x3881c`), with additional `u32` fields at `+0x10`, `+0x14` and `+0x18`. The timeout path selects `(requestID-1) mod 38` (`0x38bf0..0x38c08`) while writing the current callback request ID. Therefore metadata request ID does not always identify the request that supplied the timestamp.
- The pinned HIDL/PVR traces show buffer handles/configuration crossing the QuickCamera bridge; HIDL `OnBufferReady` carries a buffer index. The traced PVR `DeQueueFrame` copies metadata `+0`, `+8`, `+0x10`, `+0x14`, `+0x18` into `FrameMetaDate` (`0x6b7fc..0x6b820`) without visible clock conversion. The reports do not associate these values with `V4L_EVENT_CAM_REQ_MGR_SOF` or `_SOF_BOOT_TS`.

| Claim | Status | Basis and limit |
|---|---|---|
| A Pico QuickCamera CSL message contains request-ID and 64-bit timestamp-like fields | `STATIC PASS` for traced fields | SHA-pinned userspace ELF dataflow described in P3-A3/P3-A4. |

| Matching event name proves a common clock or frame identity | `NOT ESTABLISHED` | Names alone do not define clock domain or producer/consumer correlation. |
| Pico `FrameMetaDate` timestamp is physical SOF or exposure start | `NOT PROVEN` | No matched kernel contract, sensor semantics or independent physical reference. |

## Evidence required to close SOF provenance

1. Obtain the exact Pico kernel source/header revision corresponding to the observed build (including vendor patches and configuration), then inspect event definitions, payload structures, version guards and the complete CSID-to-request-manager dispatch path. The source must identify which clock is written and where request/frame IDs originate.
2. Establish an explicit bridge from that kernel event and its IDs to the QuickCamera CSL message and PVR metadata for the same request/frame. A shared label, plausible timestamps, equal counters, or a matching numeric event name is insufficient.
3. To claim physical sensor SOF or exposure timing, require version-matched sensor documentation/source defining that event's physical point. If documentation is insufficient, a separately authorized optical reference experiment must compare a controlled light transition with sensor timestamps and state its uncertainty. A system delivery timestamp, PVR dequeue time or QTIMER-like value alone is not exposure start.

## Recommendation

**Continue with targeted offline source acquisition and comparison first.** This has the highest expected information value with no camera timing impact: it can determine whether the two named event contracts exist in the relevant kernel version and expose their payload/clock fields. Do not repeat the completed node inventory for SOF provenance. Keep any SOF runtime/optical experiment `BLOCKED` until a build-matched event definition and a safe observation method are available; such a hardware study would need its own explicit scope and approval.
