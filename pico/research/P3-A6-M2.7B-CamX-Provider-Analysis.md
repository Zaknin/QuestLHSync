### Offline static analysis of the acquired provider

Analysis used Android NDK `llvm-readelf` and `llvm-objdump` on a temporary extraction of the already hash-verified ELF. The library was never executed. The temporary extraction was deleted after analysis. This report records bounded symbol/flow findings and selected addresses, not a full disassembly.

The provider exports `CSLRegisterMessageHandler` (veneer at `0x7d6168`, wrapper body at `0x2f8c6c`) and `CSLRegisterMessageHandlerHW` (veneer at `0x7d616c`, hardware registration body at `0x307f90`). `CSLHwInternalDefaultSubscribeEvents` has veneer `0x7d5ee8` and implementation `0x30d324`. The subscribe implementation builds a V4L2 subscription payload and issues request `0x4020565a` through `CSLHwInternalDefaultIoctl` at `0x30d350`, which calls `ioctl` using the FD held at `CSLHwDevice+0xc4`. The inspected event-subscription path is a direct V4L2 ioctl path; it is not the PVR QBUF/DQBUF `DefaultIoctl2` envelope path.

The provider has `VIDIOC_DQEVENT` paths at `0x3140e0` and `0x3201a0` that issue request `0x80885659`. The associated V4L2 event is inspected as an outer event header plus CRM payload. The binary reads session handle at event `+0x08`, request ID at `+0x10`, frame ID at `+0x18`, timestamp at `+0x20`, link handle at `+0x28`, and event ID at `+0x60`. A selected dispatch path constructs a `CSLMessage`: event request ID is copied to message `+0x08`, the frame-ID/timestamp pair is copied from event `+0x18` to message `+0x10`, link data and marker fields are populated, then the stored callback is invoked indirectly around `0x313ad0`. Event/session/link branches are present. Before dispatch, the zero-request-ID test allows event IDs 0 and 1 to continue but skips IDs greater than 1; therefore a zero-ID event 2 does not follow the same path as event 0. This is an observed binary branch condition, not a general kernel guarantee.

For the event-ID-0 construction branch (`0x313ccc`), the binary sets the two 32-bit marker words at `CSLMessage+0x24` and `+0x28` to 0 and 0. For event ID 2 (`0x313b48`), it stores the packed value produced by `movi v8.2s,#1`, giving marker words 1 and 1. The pair is structurally consistent with the public CamX M2.6 mapping of SOF ID 0 to Qtimer/`bNotify=false` and SOF_BOOT_TS ID 2 to Mono/`bNotify=true`; the Pico provider also contains the `CSLTimestampTypeQtimer` string. This verifies the marker values and branch structure in the installed provider ELF, while the names/semantics remain a cross-source compatibility inference until an exact kernel build mapping is available.

`CSLRegisterMessageHandler` forwards registration to the hardware implementation around `0x307f90`; the callback and context are retained in the provider's registration structure and the event path later indirect-dispatches the callback. The pinned QuickCamera binary has the existing registration callsite at `0x37d14` and its handler at `0x375d0–0x37724`; it reads request ID at message `+0x08` and a 64-bit timestamp-sized value at `+0x18`. `quickcamera.core.so` declares `DT_NEEDED camx_core.so`. Together these bytes establish a static structural bridge from provider event dequeue to its registered callback interface and a compatible QuickCamera handler. They do not establish that Android's loader selected this path in a live process or that the callback ran.

The provider binary copies a 64-bit timestamp field into the CSL message and writes timestamp-marker fields; this path does not demonstrate an intervening unit conversion. The acquired provider alone does not establish whether those bits are raw QTIMER ticks, QTIMER-derived nanoseconds, BOOTTIME/monotonic nanoseconds, or another kernel-selected source. M2.5's pinned Phoenix source shows online QTIMER-nanosecond and derived-BOOTTIME paths, an offline BOOTTIME path, and an optional frame-header timestamp path; M2.6's public CamX bridge maps event IDs 0/2 to the marker pairs observed above. There is no exact build mapping from this Pico firmware to the Phoenix pin, and no runtime setting shows which source was active. Do not transfer those source clock interpretations to this binary without a verified matching kernel contract. The provider copies the CRM payload request ID into CSL unchanged, but that does not prove equality with a request ID at another interface; the public CamX source explicitly remaps CSL sync IDs to pipeline request IDs. Nor does static branch presence prove fallback occurrence.

The provider has a `CSLHwFindPipelineIndex` implementation and diagnostic strings for CRM SOF event/frame/request fields, which support the inspected pipeline/event handling context. Static ELF analysis does not show which event source was selected for a given stream, `use_frame_header_ts` configuration, offline-context selection, or whether QuickCamera received any specific event during the acquisition. Installed `DT_NEEDED` declarations identify linkage intent only, not a runtime-resolved dependency graph.
